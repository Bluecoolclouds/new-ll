# Какие обновления upstream нужны APINET

Проверено 23 сентября 2026 г. Полный перечень: [365 коммитов](./upstream-commits-2026-09-23.md).

## Метод и ограничения

- Сравнивались текущий локальный снимок `fa285febc` и `QuantumNous/new-api` `996adffe5`. Общей Git-истории нет; ориентир для списка — upstream `8739c05c0` от 8 июля. Поэтому «365» означает коммиты **после выбранной точки upstream**, а не 365 гарантированно отсутствующих исправлений.
- Проиндексированы названия всех коммитов списка; для выбранных приоритетных исправлений проверены затронутые файлы upstream и соответствующие места локального кода. Это **триаж для переноса**, не построчный аудит всех 365 изменений, не аудит доказанной эксплуатации и не гарантия полноты каждого изменения. При совпадении поведения уже существующую реализацию нужно оставить.
- Ниже «нужно» означает **проверить и адаптировать исправление**, а не выполнять `git merge` или слепой `cherry-pick`. Upstream переместил `web/default` в `web`, вынес преобразования протоколов в `relaykit`, добавил систему плагинов. APINET сохраняет собственные платёжные обработчики и интерфейс.
- Ничего из перечисленного здесь не применено к продукту: созданы только эти документы.

## Не переносить сейчас

- Полная миграция на `relaykit` ([`86ac0f774`](https://github.com/QuantumNous/new-api/commit/86ac0f774)) и переписывание задач на плагины ([`eb48396d5`](https://github.com/QuantumNous/new-api/commit/eb48396d5)): большие архитектурные изменения без непосредственной необходимости для перечисленных исправлений. Их запускать только как отдельные проекты с регрессионными тестами.
- Новый WebSocket Responses, переработка редактора цен/каналов, перестройка `web/`, косметика интерфейса, документация и upstream release/CI workflows: нет подтверждённой потребности APINET, высокая вероятность конфликтов с фирменным UI и сборкой. Возвращаться к отдельным возможностям по запросу.
- Upstream-повышение `golang.org/x/crypto` до `v0.52.0` не требуется: в APINET уже установлена более новая `v0.55.0`. Не понижать зависимость.

**Рекомендуемый порядок:** сначала предотвращение потерь при оплате и защиту аккаунтов; затем корректность списаний/конвертаций API; после этого условные исправления по фактическому использованию функций. На каждом шаге сверять местный код, писать регрессионные тесты и не менять существующую структуру форка без необходимости.
